# 08 method：把模糊的工作变成可验证的变更

状态：v1 草案。来源于旧项目的方法论设计，已去掉企业系统与具体工作项；只讲方法与它和内核的接口。

## 1. 定位

框架由三块组成，各回答一个问题：

| 部分 | 回答 | 文档 |
|---|---|---|
| **Watch**（内核） | 做什么、谁来做、盯到什么时候 | 01、02、06、07 |
| **method**（方法论层） | 接下的工作怎么做对 | 本文 |
| **outbound**（交付层的对外写） | 对外的事什么时候问人 | 04 |

一条链：外部变化 → Watch 接活并派给执行方 → 执行方按 method 把事做好 → 对外交付经 outbound 确认。

**method 解决的问题**：通用方法论（brainstorming、规格驱动开发等）假设输入是「一个知道自己要什么的人坐在会话里描述需求」。真实的输入常常是一句话、一张图、一段转述；提需求的人不在会话里；模型分不清自己「还没弄清楚」；要改的是一个已经在运行、有多个版本线的系统。把这样的输入直接交给通用方法论，它们会把猜测整理成整齐的方案，**把猜测当成需求，做得又快又工整**。这是最需要防的失败。

**价值主张**：把模糊的工作变成可验证的变更。五个优势：

| # | 优势 |
|---|---|
| A1 | **意图还原**：从不清晰的输入还原出可以动手的意图，知道什么时候该问、问谁、怎么问；问不到时把假设登记下来，验收时回头核对 |
| A2 | **存量优先**：先写清现状行为，再写要变成什么；「不能变的行为」是一等公民 |
| A3 | **上下文接入**：工作项来源、分支规则、知识库、历史变更、接口与库表现状，在分析和设计时直接可用 |
| A4 | **可核查的证据链**：工作 → 意图 → 契约 → 提交 → 验证 → 变更说明，每一环都有 CLI 能查到的事实（确认按内容哈希、验证绑定代码快照、任务按提交识别），不靠模型自觉 |
| A5 | **知识闭环**：每次变更都给现状文档与知识库留下增量，下一个工作的分析从这里开始 |

## 2. 分层与规矩

method 分为**内核**（方法本身，不依赖任何外部系统，单独就能用）与**适配**（把内核接进具体的工作项来源、知识库、交付流程）。在框架看来，method 内核是一个可替换的方法论，外部相关的东西都在适配里。

| # | 规矩 | 怎么核对 |
|---|---|---|
| K1 | **依赖单向**：适配依赖内核，内核不依赖适配。method 内核只用标准库，**不导入 Watch 内核的任何包**，也不调用 `craft` 的其他命令；交付层只经 method 的 CLI 调用它 | 测试扫描导入与命令调用 |
| K2 | **内核不写外部系统的专有事实**：字段名、内网地址、真实编号、产品术语、宿主私有路径。需要就经端口取 | 禁用词表扫描 |
| K3 | **内核能单独跑通**：不装任何扩展，只用 git 加 method CLI，就能从一段需求文本走到本地提交与变更说明 | 端到端测试只装 method |
| K4 | **数据格式归内核**：模板、确认记录、验证证据、任务进度的格式由 method 定义并带版本号；适配读写同一种格式，同一种事实只存一处 | 格式测试在内核，适配测试只验证接线 |
| K5 | **skill 分层引用**：内核 skill 只讲方法，不引用适配的文件；外部规则由适配在入口处补给模型 | 检查引用路径 |
| K6 | **适配只加不改**：外发分级、环境白名单等交付规则在交付层把关，不去改 method 的判据；确需不同表现就给 method 加配置项 | 评审 |
| K7 | **宿主中立**：不写宿主名分支 | 宿主矩阵测试 |
| K8 | **示例脱敏**：示例与默认做法的事故出处都要脱敏 | 同 K2 |

CLI：命令组 `craft method ...`。method 是**默认且 v1 唯一**的方法论；接口上保持可替换（交付层只通过 `method` CLI 与交接包交互），将来可接入其他方法论，但 v1 不做。

## 3. 核心模型：意图 → 契约 → 证据

```
外部工作项（常常不清楚）
   │  意图还原：规则、例子、问题、假设、非目标
   ▼
意图模型 ──── 分析阶段产出，进交接包
   │  写成契约
   ▼
变更契约 = 行为契约 + 方案决定 + 验证计划 ── 人确认（method confirm）
   │  写成两份给人读的文档：需求说明、方案说明
   │  按契约实现
   ▼
证据 = 复现、任务验证、收尾验证、独立验证、现场验收 ── 逐条对回行为契约
   │  沉淀
   ▼
现状文档、知识库、变更说明 ── 下一个工作的输入
```

一套编号贯穿始终：意图模型里的例子变成需求说明里的验收场景 `S-n`，方案说明的验证一节写明 `S-n` 由哪条测试证明，独立验证逐条报告 `S-n` 的结论，变更说明的「守护测试」列出它；意图里登记的假设是 `A-n`。**任何一条行为都能从来源追到测试，也能从测试追回来源。**

### 默认做法

只留少数几条，每条有对应的事故或理由。它们是**人没说时**的默认做法，不是拦人的门：

| # | 默认做法 | 为什么 |
|---|---|---|
| L1 | **意图没还原就不写契约**：还有没答的问题时，要么问清，要么由人把它转成登记的假设 | 按猜测记「需要修改」是最贵的错误 |
| L2 | **每条行为都有例子**：规则不配具体例子，不算写清 | 抽象描述两个人能读出两种意思，例子读不出两种 |
| L3 | **写出不能变的行为**：缺陷、改已有行为、技术改造，至少一条「不变」，并且有守护 | 存量系统里最贵的错误是改坏了别的东西 |
| L4 | **缺陷先找到根因再修**：根因落到代码证据（文件:行与因果链）；能复现就复现，复现不了不拦，但要如实写明根因确定到什么程度、靠什么判断 | 修症状不修根因会返工；很多缺陷要特定环境才能复现，故不强制复现 |
| L5 | **完成看证据，不看声明**：收尾验证与当前代码一致，独立验证有真实报告；没收到验证者报告不能记通过 | 防「没有验证者回执就记了通过」 |
| L6 | **连续 3 次修不好，回到方案** | 每次修补都暴露新问题，说明方案或理解错了 |

**人的明确要求优先**：人说「直接改」「不用写方案」就直接改，不再请人确认，不限档位；记 `design-skipped`，出口不因没有方案报缺口。人的要求放宽的是过程，**不放宽说实话**（L5：没验证就说没验证）。对外写的把关在 outbound，不归 method 管。

## 4. 意图还原：力度随清晰度伸缩

不是每次都走的重流程。需求清楚时，它收缩成一段「我的理解」，请人确认后直接进方案，和通用方法论一样快；这时 method 的价值转到方案质量（几种做法对比、影响范围有依据）和证据上。

- **清晰度**决定在意图上花多少功夫；**风险**决定在方案与审查上花多少功夫。两者互不替代。
- **意图模型**的骨架借自 Example Mapping：**规则、例子、问题、假设（`A-n`）、非目标**。规则太多说明工作太大；问题太多说明还没准备好。澄清时「给一个例子」优先于「请说明需求」，例子直接变成验收测试。
- 问题要问在点上：答案确实改变方案才问；问谁（提需求的人、会话里的开发、知识库）、问几轮。问不到时登记为假设，验收时回头核对。
- **无人值守时没人可问**：只写意图模型的草稿、候选理解和问题，不进入契约。
- 意图还原放在**交付层的分析阶段**执行，意图模型作为分析报告的一部分经交接包交给方法论，所有方法论都受益；method 的优势是这一步**无损**。

## 5. 工作类型

行为契约的写法随类型变化，类型由模型提议、人确认时可改；一次变更可兼有几种类型，按主类型写契约，其余并入验证计划。

| 类型 | 行为契约怎么写 | 关键证据 | 主要风险 |
|---|---|---|---|
| 缺陷 | 现状（错误行为）/ 期望 / 不变 | 根因的代码证据；能复现时修复前失败、修复后通过 | 修了症状；改坏别处 |
| 新增能力 | 规则 + 例子（正例、反例、边界） | 每个例子都有验收测试；接口与库表增量 | 理解错需求；漏边界 |
| 改已有行为 | 变更前 / 变更后 / 不变；兼容与迁移 | 表征测试固定「不变」；新旧数据与旧调用方 | 旧数据、旧调用方、其他版本线 |
| 技术改造 | 以「不变」为主；性能、安全写可度量指标与基线 | 表征测试；改造前后指标对比 | 行为悄悄变了；指标没有基线 |
| 数据与配置 | 执行前 / 执行后状态；幂等；回退 | 多环境执行记录；回退演练 | 锁表、丢数据、各环境不一致 |
| 前端页面 | 交互场景（在什么页面、做什么、看到什么） | 四层验收：算法、组件、浏览器、用户验收；单测不能冒充浏览器验收，用户验收只能由用户本人给出 | 用单测冒充页面验收 |
| 跨仓库 / 前后端 | 接口契约先行，以后端为准；两边各自的契约引用同一份 | 两边对接口的测试 | 两边理解不一致 |
| 探索 | 不写行为契约，只写要回答的问题 | 结论与依据 | 原型被当成交付 |

## 6. 按风险分档

档位**看风险，不看篇幅**。能由脚本判断的事实（改没改接口、库表、配置；涉不涉及多个仓库；改的是不是公共模块）由 CLI 给出建议档位，模型提议，人在确认时定。

| 档 | 条件（满足任一即升档） | 要写什么 | 怎么审 |
|---|---|---|---|
| 轻 | 单点修改；不动接口、库表、配置；不改公共逻辑；行为条目不超过 3 条 | 行为契约 + 一段方案（缺陷含根因）；不写任务清单 | 人确认契约；独立验证可在本会话里做并如实写明 |
| 标准 | 默认 | 意图模型引用 + 完整契约 + 任务清单 | 人确认；收尾后独立验证 |
| 重 | 动接口或库表；数据迁移；跨仓库；改公共逻辑或对外契约；规则超过 6–8 条 | 标准档全部 + 影响范围的依据（调用链、检索结果）+ 兼容与回退方案 | **确认前**加一次独立评审；收尾后独立验证 |

做到一半发现档位不对，**回到方案升档**，重新确认。档位只决定写多少、审几次，**不豁免默认做法**。

## 7. 各环节做法

- **分析**：把推测变成证实。缺陷落到代码证据；改已有行为、技术改造先用表征测试固定「不变」；新增能力确认「现状」与代码一致并沿用已有约定。交接包里已定的结论不重做，发现它错了就停下告诉人。
- **设计：两份给人读的文档**。判断标准：一个没参加会话的人从头读下来，几分钟内能说出「要解决什么、改成什么样、为什么这么改、怎么证明改对了」。
  - **需求说明**：为什么做、要做成什么样、不做什么、怎么算做对（背景、目标与范围、业务规则、验收场景、假设与待确认）。确认后基本不动，可直接转给测试和产品。
  - **方案说明**：怎么做、为什么这么做、放弃了什么、影响谁、怎么验证（结论、根因、设计、考虑过的其他做法、影响范围与兼容、接口与库表变更、验证）。实现中可能修订。
  - 轻档两份合一。编号只作锚点，正文是成段叙述，不是规格条目。
- **编码**：标准、重档按验证方式拆任务，每个任务写明负责哪几个 `S-n`、钉死的接口与签名、证明它做对的那条测试，函数体不写进计划；标出依赖，互不依赖且不改同一文件的标为可并行。缺陷能复现就先复现。每个任务只跑窄验证、按任务提交，提交说明带 `Task:` 行（续做靠它）。**范围纪律**：不顺手重构，不改契约之外的代码，发现契约外的问题记下来告诉人。契约写错了就回去改契约并重新确认，不在代码里悄悄偏离。用到平台组件、接口、错误码前先查知识库。
- **验证**：三层——任务窄验证；收尾验证（改动模块的全部测试，留证据）；全量回归归 CI。**独立验证按验收场景逐条报告**：每个 `S-n` 给出通过、失败或无法验证并附证据位置；验证者只拿需求说明、方案说明、diff、收尾记录，不拿实现时的推理过程。意图里的每条 `A-n` 列为「待人确认」，交付时一起交给人。
- **沉淀**：接口与库表的增量合进现状文档；变更说明由需求说明与方案说明投影生成，成为 MR/PR 描述；意图还原中发现的业务口径交给知识沉淀，人定写不写。

## 9. 端口

method 内核通过端口接外部世界，每个端口带一个默认实现用于单独使用；适配提供外部系统的实现。

| 端口 | 内核要什么 | 默认实现 | 适配实现（示例） |
|---|---|---|---|
| 工作项来源 | 原始需求文本、附件、关联需求 | 对话里的文字、Markdown 文件 | 某工单系统的详情与描述缺口（由对应扩展提供） |
| 知识源 | 按关键词查到的相关文档与出处 | 仓库内文档与历史变更 | 企业知识库、历史变更与评审记录 |
| 状态存放 | 确认记录、验证证据、任务清单的读写 | 项目内被忽略的状态目录 | 写入 Craft 状态库对应记录 |
| 交付 | 出口时交出什么、交给谁 | 止于本地提交，输出变更说明 | 经 outbound：建 MR/PR → 部署 → 提测 |

## 10. 与 Watch、outbound 的接口

| 方向 | 内容 |
|---|---|
| Watch → 执行方 | Work 被接下后派给执行方会话；会话里的执行方按 method 做事。派工首条的「怎么做」指向 method 的执行手册，**Watch 不规定阶段与步骤**，只给目标与规则 |
| 交接包 → method | 已定结论、代码位置、已查知识、层内规则，加上意图模型 |
| method → 确认 | 需求说明、方案说明交给 `craft method confirm`（按内容哈希）。**这是本地「人的决定」，不是对外写**，不经 outbound；它引出的对外后果（建 MR/PR、部署、提测）到那一步再按 04 分级确认 |
| method → 验证 | 按 `S-n` 逐条的结构化结论 |
| method → 交付 | 变更说明（由需求说明与方案说明投影生成） |
| 出口核对 | 需求说明里没有未答的问题；每个 `S-n` 在方案说明的验证一节里都有证据；只对 method 方法生效 |
| 进度 | `flow` 是纯函数、无 IO，只算给人看的进度：不规定下一步、不驱动模型；阶段每次现算，不缓存、不另存「当前阶段」；骨架按问题类型定义节点，阶段可跳过 |

### 团队模式（v1.1）

标准档、重档的任务按依赖与目标文件算出可并行的波次，满足条件时主会话当调度者，把同一波任务分给宿主子代理（worker）并行实现，只读子代理（reviewer）逐任务把关，主会话集成、验证、按任务提交。**不开新会话、不经 Watch 派工**——这是单个 Work 内部的并行，不是 Work 之间的并行。子代理不改 Git 配置、不跑会改仓库的脚本、不写工作记录，**说完成不算完成**，以主会话验证为准。worker 隔离优先复用宿主自带的 worktree 能力，做不到就共用工作区或串行。默认开关按「顺序与并行的对照评测」结果再定。

## 11. 怎么证明它值得

自己维护一套方法论有成本，只有在同一批工作的评测上满足下面两条才算值得：

1. 在**返工率、无依据通过、需求理解错误**三项上，不差于「交付层 + 通用方法论」，且至少一项明显更好；
2. 篇幅与耗时不高于它们。

做不到，就把 method 收窄成「为第三方方法论准备意图与上下文的适配」，不再自己维护完整的方案与实现流程。

评测用固定的一组工作（脱敏、录制 fixture），分类别各若干条：描述清楚的缺陷、**描述清楚的需求**（通用方法论的主场，耗时与篇幅不能更差）、**描述模糊的缺陷与需求**（有没有按猜测动手、问题是否问在点上）、新增能力、改已有行为、数据与配置。指标：需求理解错误、无依据通过、首次确认通过率、返工轮数、文档篇幅、端到端耗时与调用次数。

**按模型瘦身**：每次换主力模型，逐条去掉一条默认做法或一项必写内容，看指标有没有变差，没变差就删掉。
